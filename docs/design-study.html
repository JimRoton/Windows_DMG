Design study · 9 September 2026

Mounting DMG on Windows

A feasibility assessment and layered architecture for reading — and, conditionally, writing — Apple UDIF disk images from Windows, either as a real drive letter or as a standalone application.

Q1 · A virtual drive

Yes — three viable routes, and the cheapest needs no driver you write yourself.

Windows will hand you a drive letter through a user-mode filesystem (WinFsp), through its own VHD stack, or through a kernel storage miniport. Only the third requires code signing and kernel risk.

Q2 · An application

Yes — and it is the same engine with a different head.

The container format is already parsed today by 7‑Zip, dmg2img, QEMU and others. A browser app is the low-risk first deliverable; the mount is a presentation layer on top of it.

§1

One correction to the premise before anything else

The hard part of a DMG is not the filesystem. It is the container. A .dmg is a wrapper — Apple's Universal Disk Image Format — that holds a compressed, chunked copy of a disk's sectors. Before any filesystem question arises you have to reconstruct that sector stream, and that is where the real work lives.

Second, "Apple proprietary filesystem" is not the wall it sounds like. HFS+ has been publicly specified by Apple since 2004 (Technical Note TN1150) and has been implemented openly many times over. APFS has a published Apple reference too. Both are readable. What is genuinely hard is writing to them — and that difficulty is independent of Windows.

Third, and this one matters for scope: the exFAT assumption is a fair simplification but it is not what you will actually meet. Disk images downloaded from the internet are overwhelmingly HFS+, because that is what application installers ship as. A tool that only handles exFAT will open almost nothing you find in the wild. Design for HFS+ read from the start, and treat exFAT as the case where writing becomes tractable.

Where the difficulty actually sits

Reading the container: solved, well-understood, a few thousand lines. Reading HFS+ or APFS: solved, but detail-heavy. Writing into a compressed container: mechanically awkward but bounded. Writing into HFS+ or APFS: the only genuinely dangerous part of this project — and the one place the design below deliberately refuses to go.

§2

Question 1 — can Windows show a DMG as a drive?

It can, in three different ways. They differ in one respect that governs everything else: who implements the filesystem. If you implement it, you can support HFS+ and APFS but you write far more code. If Windows implements it, you write almost nothing but you are limited to filesystems Windows already knows.

Route A — WinFsp user-mode filesystem

Recommended engine

WinFsp is FUSE for Windows: a signed kernel filesystem driver that ships with the project, plus a DLL you link against to write the actual filesystem as an ordinary user-mode service. You get a real drive letter or a UNC path. Dokany is the equivalent alternative.

  • You write no kernel code and sign nothing. A bug in your parser crashes a user-mode service, not the machine.
  • You can support HFS+ and APFS — the only route that can, since Windows has no driver for either.
  • Nothing is extracted to disk; reads are served on demand from the compressed image.
  • Licence check needed. WinFsp is GPLv3 with an exception for free and open-source software, with a commercial licence available separately. If this ever ships closed-source, budget for that licence or use Dokany instead.

Route B — the VHD shim

Ship this first

A fixed-format VHD is nothing more than raw sector data followed by a 512-byte footer. So: decode the UDIF into a raw sector stream, append a VHD footer, and hand the result to Mount-DiskImage. Windows' own storage stack and its own exFAT driver take it from there.

  • Zero driver work of any kind. Full native read and write, at native speed, with no filesystem code of your own.
  • Bounded by what Windows already mounts: exFAT, FAT32, NTFS, ISO 9660, UDF. Useless for HFS+ or APFS unless a third-party filesystem driver is also installed.
  • Costs the full uncompressed size in scratch space, and needs administrator rights to attach.
  • Writes land in the VHD, not the DMG. Getting them back requires a re-encode — see §7.

Under your stated exFAT assumption this is the correct answer, and it is a weekend of work rather than a quarter.

Route C — virtual SCSI / StorPort miniport

Only if you need raw disks

A kernel storage driver that presents the decoded image as a physical disk, the way Arsenal Image Mounter does. Windows then mounts the volume itself.

  • Requires an EV code-signing certificate and attestation or WHQL signing to distribute. You own kernel-mode crash and bugcheck risk.
  • It still does not solve HFS+ or APFS — there is no Windows driver to hand them to.
  • Worth it only if you specifically need \\.\PhysicalDriveN semantics for forensics or imaging tools.

Route D — Windows Projected File System

Wrong shape

ProjFS (the mechanism behind VFS for Git) projects a virtual namespace into a directory, not a volume. It ships in Windows, requires no signing, and would give a serviceable browse-and-copy-out experience — but its hydration model is built for source trees, write-back is awkward, and it cannot present itself as removable media. WinFsp does the same job better here.

The recommendation

Build the decoder once and treat every route as a head on it. Ship the VHD exporter first because it is useful within days; add the WinFsp mount when HFS+ support lands. Do not build Route C unless a specific requirement demands it.

§3

Question 2 — the application, and the prior art that proves it

This is settled by existence proof. The UDIF container is read today by 7‑Zip, by dmg2img, by the dmgwiz Rust crate, by QEMU's block/dmg.c, and by darling-dmg. Several of those also walk HFS+. None of it is speculative.

What none of them do well is the part a user actually wants: a coherent Explorer-like browser with correct filename handling, working extraction of HFS+ compressed files, and drag-and-drop back out. That is the gap, and it is a user-experience gap rather than a format one.

§4

What you actually have to parse

UDIF is read from the back. The last 512 bytes of the file are the koly trailer, identified by the magic koly (0x6B6F6C79). It carries the offset and length of the data fork, the offset and length of an XML property list, the total sector count and a set of checksums.

That property list holds a resource-fork dictionary containing an array of blkx entries. Each entry's payload is a base64-encoded mish block (magic mish, 0x6D697368) describing one region of the disk: its first sector, its sector count, a base offset into the data fork, and then a list of 40-byte chunk descriptors.

Container variants to detect and route

  • UDRW / UDTO / raw — uncompressed. Effectively a raw image with a koly trailer. The only variant you can write into cheaply.
  • UDZO / UDBZ / ULFO / ULMO — compressed, the common distribution formats.
  • Encrypted — an encrcdsa header at the front of the file instead. Passphrase to PBKDF2 to an unwrapped AES key. Defer to v2, but detect it and say so rather than failing with a parse error.
  • NDIF (classic Mac OS .img), sparseimage and sparsebundle — different containers entirely. Detect and report; do not attempt in v1.
§5

The architecture — one core, several heads

The whole design turns on a single seam. Layers L0 to L3 together do exactly one thing: turn a .dmg file into something that answers read(offset, length) like a plain disk. Everything above that seam believes it is talking to ordinary hardware and does not know DMG exists.

That is what lets the GUI, the CLI, the VHD exporter and the WinFsp mount all be thin. It is also what lets you test the hard half in isolation, against dmg2img output, with no driver installed and no Windows involved at all.

L0

Byte source

Memory-mapped file, or a stream. Isolates the one place that touches storage, so an HTTP range-request source can be dropped in later without disturbing anything above.

L1

Container parser

Sniff UDIF / NDIF / raw / encrcdsa. Read the koly trailer, parse the plist, decode every blkx into mish blocks and chunk descriptors. Produces an extent list, nothing more.

L2

Extent index and chunk cache

The extents sorted into a flat array keyed by start sector, so a read is a binary search. An LRU cache of decompressed chunks sits here — without it the design does not perform. A sidecar index file avoids re-parsing the plist on every mount.

L3

Codecs

zlib, bzip2, LZFSE, LZMA, ADC, raw and zero behind one decompress(in, out, expectedSectors) signature. Each one hard-bounds its output against the descriptor's declared sector count.

―

IBlockDevice  —  read(offset, length) → sectors

L4

Partition mapper

Driver Descriptor Map at sector 0, Apple Partition Map, GPT behind a protective MBR, or no table at all. Emits the set of volumes and their sector ranges.

L5

Filesystem readers

Pluggable behind one interface: exFAT and FAT32 (read and write), HFS+ and HFSX (read), APFS (read only), ISO 9660 and UDF (read). Each one is independently testable against a fixture image.

L6

VFS — the Mac-to-Windows mapping

Names, timestamps, forks, links, permissions. Small in code and large in bugs; §6 is entirely about this layer.

—

Heads

WinFsp mount host, VHD exporter, GUI browser, CLI, Explorer shell extension. Parallel consumers, not a further layer — each is a few hundred lines over the core.

§6

The layer everyone underestimates

L6 is where a technically correct reader becomes a usable one. None of these are hard individually; all of them are silently wrong if skipped, and several produce the specific failure of "the file is there but it's empty."

Names

  • Unicode normalisation. HFS+ stores filenames decomposed (NFD, and a specific Apple variant of it). Windows expects composed (NFC). Compose on the way out, decompose on lookup, or accented names will not round-trip.
  • Illegal characters. A colon is legal in an HFS+ name and illegal on Windows — as are \ / ? * " < > |, trailing dots and spaces, and the reserved names CON, PRN, AUX, NUL, COM1–9, LPT1–9. Map them to their fullwidth equivalents so the substitution is visible and reversible.
  • Case sensitivity. HFSX and APFS may be case-sensitive; a Windows volume is not. Two files differing only in case will collide — detect it and disambiguate rather than dropping one.

Content

  • Transparent compression. This is the one that catches everybody. Files on a Mac volume are frequently stored compressed, with the payload hidden in a com.apple.decmpfs extended attribute — inline for small files, or as a chunked table in the resource fork for large ones, using zlib or LZVN. A reader that ignores it reports a great many files as zero bytes and looks broken. It must be implemented, not deferred.
  • Resource forks. Map to NTFS alternate data streams, or drop them deliberately — but decide, and document it. Hide the ._name AppleDouble companions rather than showing them as junk.
  • Hard links. HFS+ implements them as indirect nodes pointing into a hidden private directory. Resolve them or the file appears as an unreadable stub.

Metadata

  • Three time epochs. HFS+ counts seconds from 1904‑01‑01 in local time; APFS counts nanoseconds from the Unix epoch; Windows counts 100‑nanosecond ticks from 1601. Every conversion is easy and every one is easy to get subtly wrong.
  • Permissions. There is no useful mapping from uid/gid/mode to a Windows ACL. Synthesise a sensible one; surface the Mac "locked" flag as read-only.
  • Housekeeping files. Mark .DS_Store, .fseventsd, .Spotlight-V100, .Trashes and .VolumeIcon.icns hidden and system, so the drive opens looking like the Mac window it is meant to mirror.
§7

Writing — the honest answer, and the design that makes it survivable

Writing is two separate problems that people usually conflate.

Writing into the filesystem. exFAT is tractable: the specification is published, the structures are simple, and there are working implementations to check against. HFS+ is risky — catalog and extents B-trees, an allocation bitmap and a journal, all of which must stay consistent or the volume will not mount on a Mac again. APFS is effectively off the table: copy-on-write, checkpoints, an object map, a space manager and Fletcher‑64 checksums throughout. Do not write APFS.

Writing into the container. Into an uncompressed UDRW image this is trivial. Into a compressed one it is not: changing one sector invalidates its chunk, recompressing that chunk changes its length, and every subsequent chunk's CompressedOffset then shifts — which means rewriting every mish table, the koly trailer and all the checksums. That is a full rewrite of the file.

An overlay resolves both. Writes never touch the image; they land in a sparse sidecar keyed by sector, with a dirty bitmap deciding, per sector, whether a read is served from the overlay or falls through to the base. Commit is a separate, explicit act.

The one thing not to do

Do not offer in-place writes to HFS+ or APFS on an image the user cares about, however well the read path is going. A half-updated B-tree or a stale journal produces a volume that Disk Utility refuses to mount, and the user will have no copy. If HFS+ write ever ships, ship it overlay-only, with commit writing a new file — never over the original.

§8

Performance and security — the two constraints that shape the code

Performance

  • Cache sizing is the single most consequential number. Default to 64 MiB of decompressed chunks; make it configurable. Below roughly a dozen chunks, directory traversal in a large image degrades badly, because metadata reads scatter across chunks.
  • Prefetch on sequential detection. When consecutive reads advance monotonically, decompress chunk n+1 on a background thread. This is most of the difference in copy-out throughput.
  • Persist the index. Parsing the plist and every mish block takes milliseconds, but doing it on every mount is visible. Cache it in a sidecar keyed on path, size, mtime and the koly checksum.
  • Let the OS cache the compressed bytes. Memory-map the data fork rather than reading it; the page cache then holds the hot compressed regions for free.
  • Do not hydrate under the mount. Extracting the whole image to disk under a WinFsp mount defeats the point — that behaviour is Route B, and it should be an explicit user choice, not a hidden fallback.

Security

Every byte of a DMG is attacker-controlled — these files arrive from the internet — and in the mount configuration your parser sits directly behind a kernel driver. Treat it accordingly.

  • Bound every declared length against the real file size before allocating or seeking. CompressedOffset and CompressedLength are the obvious attack surface.
  • Cap decompression output at the descriptor's SectorCount × 512 and abort on overrun. A chunk claiming four gigabytes of output is a decompression bomb, not a large file.
  • Use checked arithmetic on all sector maths. 64-bit sector counts multiplied by 512 overflow, and the result indexes a buffer.
  • Bound B-tree traversal. HFS+ catalog nodes can be made to form a cycle; cap depth and track visited nodes.
  • Run the mount host as a low-privilege account, and consider isolating the parser in a separate restricted process behind a pipe. It costs little and contains a great deal.
§9

Build order

Ordered so that something usable exists at M3, and every milestone is verifiable against an existing tool rather than against itself.

M1

The core, minimum viable

koly, plist and mish parsing; raw, zero and zlib codecs; extent index; IBlockDevice. Two CLI verbs: dmginfo and dmgextract. Verified byte-for-byte against dmg2img output.

M2

Format completeness

bzip2, LZFSE, LZMA and ADC. Partition layer — DDM, APM, GPT. exFAT and FAT32 read. First real directory listings.

M3

VHD head — first shippable drive

Decode to raw, append the VHD footer, attach via Mount-DiskImage. A real drive letter with native read and write, for any image whose payload Windows already understands. Ship it here.

M4

HFS+ read, done properly

Catalog and extents B-trees, hard-link resolution, resource forks, and decmpfs transparent decompression. This is the milestone that makes the tool work on real downloads.

M5

Application head

The GUI browser with the L6 mapping applied: correct names, correct sizes, drag-out extraction. Shell extension for “Mount” on right-click.

M6

WinFsp mount, read-only

A drive letter over the live compressed image, HFS+ included, with no extraction. The headline capability.

M7

Overlay write and commit

Sparse overlay, dirty bitmap, exFAT write, and the re-encoder. Gated by the policy matrix in §7.

M8

Long tail

APFS read; encrcdsa decryption; NDIF, sparseimage and sparsebundle containers.

§10

Implementation notes and one licence to check

Language. Rust for the core. The argument is not taste: this is a binary parser handling hostile input whose output is consumed by a kernel driver, and the entire class of bug that has historically made image parsers dangerous is the class Rust removes. There is also existing ground to stand on — dmgwiz, lzfse, flate2, bzip2, xz2, and winfsp-rs bindings. If you would rather follow WinFsp's own samples closely, its C API with the memfs and passthrough examples is the shortest path to a working mount.

Shape of the repository. One crate for the core with no Windows dependency at all, so it builds and tests on the Mac where the fixture images are made. Separate crates for each head. The core's test suite is a set of small fixture DMGs — one per codec, one per partition scheme, one per filesystem — generated by hdiutil on macOS and checked in.

Licensing. Nothing here is circumvention: UDIF is undocumented rather than protected, HFS+ and APFS both have published Apple references, and LZFSE is Apple's own Apache‑2.0 release. The single thing to settle before writing code is WinFsp's licence — GPLv3 with a free-software exception, with a commercial option — because it determines whether the mount head can be closed-source. Dokany, under LGPL and MIT, is the fallback if the answer matters and the commercial licence does not suit.
